# DeepFuzz Poster Quality Check

| Assessment area | Poster evidence | Demo support | Status |
| --- | --- | --- | --- |
| Poster 15% | Clear title, student line, motivation, aim, method, architecture, results, analysis, contribution, scope, conclusion, references, and UQ footer branding. The layout uses one central pipeline diagram, a compact result table, charts, and short section text. | The poster can be read top-left to bottom-right and supports a 3-5 minute explanation without relying on hidden context. | Complete |
| Presentation 20% | The "Demonstration Artefacts" box gives a concrete path through seed JSON, generated pytest, coverage report, and triage report. | `poster_demo_script.md` includes a 30-second pitch, a 3-5 minute pitch, exact live commands, backup plan, and examiner Q&A. | Complete |
| Excellence / Innovation 35% | The contribution box highlights documentation-first generation, runtime grounding, validation and repair, reproducible manifests, selected-function coverage, and strict triage categories. | The live demo can show one API moving from documentation-derived seed to generated replay test and final evidence. | Complete |
| Completeness 30% | Results are from the final `*-thesis-all` runs: 1,992 accepted APIs, 1,407 generated pytest tests, 12,383 valid programs, API execution coverage for all three libraries, selected-function coverage, and candidate triage counts. | Commands use existing final artefacts and one fast replay test, so the demo can proceed even if full Stage 4 fuzzing is too slow. | Complete |
| Topic and scope | The poster states DeepFuzz as an end-to-end documentation-driven fuzzing pipeline for JAX, TensorFlow, and PyTorch APIs. | The pitch names the scope boundary: Python selected-function coverage, not whole-library native/kernel coverage. | Complete |
| Background and motivation | Motivation explains why deep-learning API testing is difficult and why documentation is useful but not executable by itself. | Examiner discussion answers address documentation reliability and why runtime validation matters. | Complete |
| Results and significance | The results table and charts show accepted APIs, generated tests, base-valid APIs, API execution coverage, selected-function coverage, valid programs, candidate bugs, and device mismatches. | The demo can open `coverage_report.md`, `bug_report.csv`, seed JSON, and generated pytest files to support the numbers. | Complete |
| Professional engineering practice | The poster points to run manifests, final reports, generated tests, coverage reports, and triage CSV/JSON files as reproducible evidence. | The script emphasises replayability, isolation, evidence trails, and conservative candidate-bug wording. | Complete |
| Visual readiness | All required visuals exist in `poster_assets/`: pipeline diagram, architecture diagram, coverage chart, readiness/execution chart, and triage chart. | The PDF is one landscape A3 page generated at 300 dpi from the final poster render. | Complete |
| Scope limits | The poster explicitly states `unavailable_on_this_run` for whole-library native/kernel coverage and uses selected-function Python line coverage as the headline metric. | The Q&A includes direct answers on native coverage and candidate status. | Complete |
